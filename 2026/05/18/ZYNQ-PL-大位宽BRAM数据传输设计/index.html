Zynq PL 大位宽 BRAM 设计实践

核心问题

AXI BRAM Controller 与 Block Memory Generator 的位宽与地址映射问题

在 Zynq 的 PL 设计中，使用 AXI BRAM Controller + Block Memory Generator（BMG） 构建片上高速缓存是一种非常常见的方案。在常规 32/64/128bit 数据宽度下，这套结构通常可以直接使用 Vivado Block Design 自动连接完成设计。

但当系统开始追求更高吞吐，例如：

  • FPGA 内部使用 256bit 数据流

  • AXI HP/HPC 接口进行宽总线搬运

  • 多通道数据聚合后以 256bit 为最小处理单元

  • 图像处理 / DMA 缓冲采用宽位宽流水

这时，AXI BRAM Controller 与 BMG 的组合会暴露出一个非常典型的问题：

AXI BRAM Controller 可以配置为 256bit，但 BMG 在 “AXI BRAM Controller” 模式下不会自动跟随位宽变化，最终导致位宽不匹配，甚至在 standalone 模式下出现 BRAM 地址异常。

本文基于一次完整工程实践，对这个问题的根本原因、AXI 地址语义以及正确的大位宽 BRAM 地址映射方法进行总结。

一、问题现象

系统结构如下：

  • PS 端通过 AXI 访问 BRAM

  • AXI BRAM Controller 数据宽度配置为 256bit

  • 后端 BRAM 使用 Block Memory Generator

  • PL 侧通过 Port B 以 256bit 宽度读取数据

在 Vivado 中，首先会遇到：

1. BMG 配置为 “AXI BRAM Controller” 模式时报位宽不匹配

原因在于：

  • AXI BRAM Controller 支持更大的 AXI 数据宽度

  • 但 BMG 的 “axi-bram-ctrl” 模式内部参数推导并不会自动扩展到 256bit

  • BRAM 位宽仍按默认逻辑生成

  • 最终导致 width mismatch

因此：

在 256bit 场景下，BMG 必须使用 standalone 模式。

随后又会出现第二个问题：

2. standalone 模式下，只有前几个地址有数据

例如：

  1. PS 连续写入多个 256bit 数据块

  2. Port B 读取时：

  • addr=0 有数据

  • addr=1 有数据

  • 后续地址全部为 0

这个现象来自：

AXI BRAM Controller 输出的是 byte address，而 BMG standalone 使用的是 word address。

二、AXI 地址的真实含义

首先需要明确：

AXI 总线地址永远是“字节地址（byte address）”。

这一点与数据宽度无关。即使 AXI 数据宽度配置为：64bit，128bit，256bit，地址仍然以 Byte 为单位递增。

八、总结

AXI BRAM Controller 与 BMG 在大位宽场景下的问题，本质上来自：

  • AXI 地址使用 byte address

  • BMG standalone 使用 word address

  • Vivado 不会自动完成两者之间的语义转换

因此：

大位宽 BRAM 设计中，地址适配层是功能正确性的必要部分，而不仅仅是接口封装。

  • 256bit 数据流

  • DAS / DMA 缓冲

  • 多通道聚合存储
